## O que foi feito

- **Toolbox por modo em runtime** (`loop.SetToolboxMode`): `plan` expõe só read-only; `run`
  adiciona `write_file` (+ `shell` se habilitado). O system prompt de plan instrui "produza um
  plano, não execute mudanças" e proíbe inventar tool_calls fora da lista.
- **Approver=interface** (`internal/loop`): interface `Approver` com `Decide` (ask) e `Vetoed`
  (kill-switch do operador que sobrepõe `allow` — §5.6.6). Novo `approval.timeout_seconds`:
  aprovação que expira recusa (fail-closed).
- **Fluxo do plano no REPL** (`cmd/ancientcode`): `Turn` plan → mostra o plano →
  `y` = `SetToolboxMode(run)` + `Continue("Aprovado: execute...")`; `n` descarta;
  `feedback:<msg>` replaneja com o retorno. `Loop.Continue` retoma do histórico sem duplicar a
  mensagem do usuário.
- **`--run`**: execução direta não-interativa; inicialização falha se `approval.write_file !=
  allow` ou `shell_tool=enabled` (sem downgrade silencioso).
- REPL migrado para um único `bufio.Reader` (fim do conflito prompts/approver).
- Versão `0.3.0-m3`.

## Testes de segurança M3 (falham se a proteção for removida)

- `TestTurnPlanModeNeverMutates` — fake provider chama `write_file` no modo plan → rejeitado,
  arquivo nunca criado.
- `TestTurnApprovalDenied`/`TestTurnDenyNeverExecutes` — `ask` negado não executa, mesmo com
  `approval.default=allow` e `write_file=ask`.
- `TestTurnVetoOverridesAllow` — `Vetoed(write_file)` recusa mesmo com `write_file=allow`.
- `TestTurnApprovedVectorIsFrozen` — o resumo aprovado é o exato vetor executado (arquivo no
  caminho aprovado com o conteúdo aprovado).
- `TestTurnApprovalTimeoutFailsClosed` — timeout de aprovação recusa e nada executa.
- `TestTurnPlanFlowReRunAfterApproval` — `Turn`(plan) + `Continue`(run) executa exatamente o
  vetor aprovado; user request não é duplicado no histórico.
