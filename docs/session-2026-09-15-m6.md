## O que foi feito

- `internal/tools/code` novo:
  - **`code_scaffold`** — gera árvore de projeto a partir de template `//go:embed templates`
    (`template.yaml` com `files[]` de `content`/`src`), placeholders `{{name}}/{{Name}}/{{NAME}}/
    {{module}}`; recusa overwrite de projeto existente, valida nome/módulo, hard-blocka
    segmentos `.git/.ssh/.env/.git-credentials` e **nunca executa** nada (templates com `.sh`,
    shebang, path-traversal, duplicatas ou `content`+`src` juntos são rejeitados na carga).
  - **`edit_file`** — patch textual por substring exata (com `occurrence` 1-based para desambiguar),
    diff `---before/+++after` no resultado, escrita somente dentro de `code_root`.
  - **`code_review`** — 100% read-only (abre só-leitura), heurísticas locais sem LLM
    (`hardcoded-secret`, `shell-exec`, `world-writable-perms` [POSIX], `path-traversal`,
    `large-binary`, `todo-fixme`, `prompt-injection`), relatório `{findings:[{file,severity,rule,
    detail}]}` redigido e truncado; conteúdo adversarial etiquetado; não modifica arquivos.
- **Confinamento**: exportei `files.Resolve`/`ResolveWrite`/`CheckSensitive` para o pacote code
  reusar a mesma lógica testada; `main.go` agora enraiza `read_file/write_file/list_dir` em
  `cfg.CodeRoot`; validação nova `code_root` strict-child de `workdir` (SPEC §10.3).
- **Loop**: `policyFor` — `code_scaffold`/`edit_file` sempre `ask`; `code_review` read-only
  (allow) e disponível também no modo **plan**; toolbox run adiciona `code_scaffold`/`edit_file`.
- Config: `code_root` validado dentro de `workdir` (fail-closed). Versão `0.6.0-m6`.

## Observações / riscos

- `world-writable-perms` é POSIX-only (Windows emula 0666/0777) — gate por `runtime.GOOS` e
  coberto na suíte WSL/Linux.
- `write_file` não produz diff "linha a linha" como `edit_file`; a prévia para o gate humano é o
  próprio resumo redigido dos args (todo o conteúdo) antes da aprovação.
- Heurística `prompt-injection` é indício, não prova; o gate humano (saída untrusted) é a defesa
  real (§10.4).
- `TestExecBasic` em Windows apresentou um flake transitório (helper-process sob carga) numa
  re-rodada; passou 3/3 isolado e não é relacionado ao M6.
